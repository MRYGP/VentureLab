# B 线单平台产品采集与人工拆解指令

> 版本：v3.3 · 2026-08-27
> 性质：一次只处理一个众筹／产品平台的批量采集与人工消化流程。不是案例发现器，不自动建立案例、假设或 TradeLab 候选。
> 北极星：从已经获得真实支持或付款信号的具体产品出发，理解用户为什么选择、产品怎样创造差异、项目怎样定价和建立信任，再由杨判断哪些机制值得改良、迁移或组合。
> 默认分工：具备本地仓库读取能力的 GPT-5.5 Codex/Cursor 环境承担同一平台的连续采集；杨决定“为什么最终值得扒”；Codex 对杨选中的产品逐个介绍、解释和核验。Claude 仅在杨点名时承担选中对象的独立审计，不作为默认采集员。

## 一、采集总量与执行批次分开

- **平台目标池**：一个平台累计 20—30 个产品，用于形成足够宽的学习面。
- **单次执行批次**：Claude 每次最多交 5 个；材料不足可以少交，不得凑数。
- **每日人工消化**：杨按自己的节奏选择 5—10 个共同拆解，一次只说清一个。
- **未选产品**：留在平台采集报告，不自动排队、不自动进入案例库。
- **切换平台**：只有杨明确说“切换平台”才切换；采满 20—30 个不是自动通行证。

这样既保留杨要求的平台宽度，也不把 25 个产品压成一次长输出。每个平台通常由同一个 GPT-5.5 Codex/Cursor 任务连续运行 4—6 批，每批开头带回累计产品名去重。

## 二、谁来判断“为什么值得扒”

分成两层，不能混写：

1. **AI 页面初筛理由**：只指出项目页上可见的具体信号，例如支持人数、产品动作、场景定位、档位结构、样机测试或跨市场表达。它只能回答“这个页面可能教我们什么”。
2. **杨的最终理由**：杨打开页面、理解产品后决定它为什么值得继续拆；也可以判断“不值得”。

AI 不得把初筛理由写成机会、商业推荐或杨已确认的学习结论。

### 2.1 一眼理解标准

采集结果不能只是一张产品名和金额表。每个产品必须形成一张紧凑学习卡，使杨无需先读完整项目页，就能快速看清：

1. 它替谁完成什么任务，替代了什么旧动作或旧方案；
2. 它在哪些维度发生了创新：原理／结构、动作、场景、形态、报价、信任或商业结构；
3. 页面上最可能解释众筹表现的 1—3 个**成功因子候选**，每个候选对应什么事实；
4. 哪些机制可以借鉴，哪些结果依赖团队、品牌、专利、制造、认证、粉丝或渠道，不能照搬；
5. 交付、长期零售、复购和利润还缺什么证据。

“真正成功的因子”必须分账：

- **众筹成功因子候选**：可以根据项目页提出，但只能记为 `I`，必须同时写页面事实和主要替代解释；
- **长期产品成功因子**：没有 Updates、Comments、交付和众筹后零售材料时，一律写 `Ø·选中后核`，不得由筹款金额倒推。

### 2.2 采集期可以标记的六类

| 标签 | 页面必须能直接看到什么 |
| --- | --- |
| `U·用户拉力` | 平台显示的支持金额、支持人数、时间或档位选择信号 |
| `M·产品机制` | 正文、图片或视频清楚展示结构、材料、动作或系统组合 |
| `S·场景迁移` | 项目页明确把既有机制带给新人群、新场景或新任务 |
| `O·报价设计` | 早鸟、套装、附加购、订阅或档位结构可见 |
| `T·信任建立` | 页面可见样机、测试、认证、团队经历、演示或风险说明 |
| `G·全球化` | 团队、生产、语言、主要市场或本地化表达具有跨市场信息 |

### 2.3 选中后再补的三类

| 标签 | 为什么后置 |
| --- | --- |
| `D·交付履约` | 需要系统阅读 Updates、评论、延期、退款和质量处理 |
| `F·失败对照` | 项目状态可能可见，但失败原因不能从结果倒推 |
| `R·零售延续` | 需要查询独立站、零售、电商、后续版本或主体状态 |

项目页若直接显示取消、未达目标或结束状态，可以如实登记状态，但不得在采集阶段填写失败原因。

## 三、为什么众筹产品值得扒

众筹项目页常把产品定义、演示、支持行为、档位、团队叙事、评论和更新放在同一对象上，也可能保留未达标、取消、延期和失败项目。这适合同时学习产品、表达、定价、信任和履约。

但支持金额不等于最终收入，支持人数不等于长期用户，众筹成功也不等于交付、复购或利润。“值得扒”不等于值得做、能够进入、可以赚钱或适合中国。

## 四、固定工作流

```text
选择 1 个平台并建立 20—30 个的平台目标池
→ 同一 GPT-5.5 Codex/Cursor 任务每批采集最多 5 个
→ 每批带回累计产品名，防止重复
→ AI 为每个产品交一张紧凑学习卡，并给页面可见的初筛理由与成功因子候选
→ 杨决定哪些最终值得扒，并选择当天消化对象
→ Codex 逐个介绍、解释并和杨讨论
→ 只对杨选中的对象补 Updates、Comments、交付、失败与零售结果
→ 杨说出自己的购买理解、改良、组合和迁移观察
→ 有具体未解决部分才进入发现门
```

第一轮默认从 Kickstarter 开始，只是执行顺序，不表示它比其他平台更适合创业。

## 五、给 GPT-5.5 Codex/Cursor 环境的专用采集指令

下面整段可直接粘贴。第 1 批的“已收产品名”留空，以后每批粘回累计名称。

```markdown
# 任务：Kickstarter 单平台产品采集（第 N 批）

你是 VentureLab 的固定平台采集员。本窗口只研究 Kickstarter，不跨平台。你的工作是从项目页提供准确、可复核的产品入口，并为每个产品制作一张能让杨快速看懂“它是什么、创新在哪里、众筹表现可能由什么驱动、哪些可借鉴或不可照搬”的紧凑学习卡。你不替杨作最终学习判断，不推荐创业项目。

## 本批参数

- 平台：Kickstarter
- 官方发现入口：https://www.kickstarter.com/discover
- 批次：第 N 批
- 本批上限：5 个；证据不足时可以少交
- 平台累计目标：20—30 个，但本批交完即停
- 运行日期：2026-08-26
- 已收产品名（只用于去重）：
  [第 1 批留空；以后由杨粘贴累计名称]
- 建议保存文件名：inbox/平台采集/YYYY-MM-DD-Kickstarter-第N批-ChatGPT5.5.md

## 取材边界

0. 开始前必须确认本任务能读取 VentureLab 本地仓库中的现行指令，并能实际打开项目正文。任一条件不满足时，只检查 1 个项目便停止并报告环境限制，不得继续生成 5 张半成品卡。普通网页版即使使用同名模型，也不自动视为等价执行环境。
1. 只从 Kickstarter 官方发现页、分类页和本次实际打开的精确项目页取材。
2. 不跨到 Indiegogo、Amazon、媒体文章或其他平台补字段。
3. 本批不进 Comments，不系统读 Updates，不查众筹后零售。这三类工作只在杨选中产品后进行。
4. 不只取金额最高的项目。尽量让 5 个产品的品类、机制或时间不同；如果页面可得，可包含当前在筹和结束较久的项目，但不得为了构成配额降低真实性。
5. 同一品牌／系列最多 1 个；与“已收产品名”重复的不得再交。
6. 无法打开精确项目页、无法确认名称或 URL 时不入选。宁可只交 3 个真的，也不交 5 个掺假的。

## 页面初筛标签

本批只允许使用以下六类：

- `U·用户拉力`：页面显示支持金额、支持人数、时间或档位选择信号
- `M·产品机制`：页面清楚展示结构、材料、动作或系统组合
- `S·场景迁移`：页面明确把已有机制带给新人群、新场景或新任务
- `O·报价设计`：早鸟、套装、附加购、订阅或档位结构可见
- `T·信任建立`：样机、测试、认证、团队经历、演示或风险说明可见
- `G·全球化`：团队、生产、语言、市场或本地化表达具有跨市场信息

`D·交付履约`、`F·失败对照`、`R·零售延续` 本批一律不判断，写 `Ø·选中后补`。项目状态可以照页面登记，但不得从状态推断原因。

## 输出格式：每个产品一张紧凑学习卡

本批最多 5 张卡，不使用超宽总表。每张卡按以下固定格式输出：

```markdown
### K-N-01｜项目页标题原文

- **精确项目 URL**：
- **平台品类／国家或地区／时间与状态**：
- **平台显示结果**：目标金额／已筹金额／支持人数／结束日期；统一标 `F-P·平台显示口径`
- **一句话看懂**：谁在什么场景，用它完成什么任务
- **原来的方案或动作**：项目声称替代、减少或重新组织了什么
- **最承重的产品机制**：真正使产品成立的原理、结构、材料、动作或系统组合；区分 `F-P·项目自述` 与 `I`
- **创新维度**：只列实际有内容的维度，不为填满而硬写
  - 原理／结构
  - 动作减少／便利性
  - 新人群／新场景／新任务
  - 形态／包装／审美／情绪表达
  - 报价／档位／套装／附加购
  - 演示／叙事／信任建立
  - 商业结构／耗材／复购
- **众筹成功因子候选（1—3 个）**：每项按“候选因子 → 页面事实 → 证据标签”写；只能记为 `I`
- **主要替代解释**：既有粉丝、媒体曝光、早鸟折扣、广告投流、品类热度或 `Ø`
- **可以借鉴什么**：只写可迁移的机制、思路或验证方式，不写“应该做这个产品”
- **不能照搬什么**：团队、品牌、专利、认证、制造能力、粉丝、渠道或其他依赖
- **长期成功仍缺什么**：交付、质量、众筹后零售、复购、利润中的关键 `Ø`
- **杨的最终判断**：待杨观察
```

填写要求：

1. 编号为 `K-N-01` 至 `K-N-05`，N 是批次号。
2. 每张卡以 350—600 个中文字符为宜；事实不足可以更短，不用空话补齐。
3. 项目名使用项目页标题；URL 必须是本次实际打开的完整项目页链接。
4. 品类使用平台页面标签；看不到写 `Ø`。
5. 时间与状态只按页面写“在筹／成功结束／未达目标／取消／Ø”及可见日期。
6. 金额和支持人数不得估算；平台显示事实不得写成真实收入、利润或长期需求。
7. 创新维度必须落到具体改变，不得只写“创新设计、用户体验好、解决痛点”。
8. 成功因子只能写“候选”；高筹款额本身不是成功原因，项目方宣称也不是独立证明。
9. “可以借鉴”指可迁移的机制，不表示产品值得做、能够进入或适合中国。
10. 如果使用 `O·报价设计`，补写一至两个最能说明结构的可见档位；不要求逐档抄录。
11. `D·交付履约`、`F·失败对照`、`R·零售延续` 没有材料时统一写 `Ø·选中后补`。

## 禁止项

- 不得构造、补全或凭记忆填写 URL；
- 不得引用本批未实际打开的页面；
- 不得填写评论原句、Updates 结论、交付结果、失败原因或零售延续；
- 不得给演示视频编时间码；
- 不得写“核心痛点、真正机会、建议做、可进入、预计利润”；
- 不得从高筹款额倒推出创新有效、产品长期成功或某个因子已经被证明；
- 不得把项目方的卖点、愿景或测试声明直接改写成成功因子；
- 不得为凑满 5 个而降低事实标准；
- 图片和视频只给页面 URL，不内嵌、不转存；
- 查不到的一律写 `Ø`，不估算、不写近似值。

## 表后自检

只回答：

1. 每个 URL 是否都来自本次实际打开的页面？
2. 是否与已收清单重复？
3. 是否有字段依靠记忆或推断填写？如有，指出并改为 `Ø`。
4. 是否误填了交付、失败原因或零售延续？
5. 是否替杨填写了最终判断？
6. 每个成功因子候选是否都有页面事实，并写了主要替代解释？
7. 杨能否只看卡片就理解产品、创新维度、成功因子候选和不可照搬条件？

交完本批即停。不要自动开始下一批，不要跨平台，不要深挖任何一个产品。
```

## 六、每批回来后的处理

1. 先保存本批原始学习卡，并把新产品名加入下一批的“已收产品名”。
2. 杨可选择：`继续下一批`、`先拆 K-N-xx`、`本平台停止`。
3. 杨选中的产品由 Codex 先做 90 秒介绍，再围绕四问讨论：
   - 为什么有人支持它？
   - 最承重的产品机制是什么？
   - 哪个部分让我觉得自然、奇怪或过度设计？
   - 我想到的是改良、组合、新人群、新场景还是新任务？
4. 只有选中后，才让 Claude 定向读 Comments、Updates、失败、交付和众筹后零售。
5. 定向材料回来后，对卡片中的成功因子候选逐项记为 `支持／削弱／Ø`；未核验前不得去掉“候选”二字。

## 七、选中后的定向补充

定向补充不重跑平台采集，只处理杨点名的项目：

1. 支持档位和价格结构；
2. Comments 中的主要质疑与团队回应；
3. Updates 的样机、制造、认证、延期、退款、交付和质量时间线；
4. 众筹后是否继续零售、迭代、停止、破产或 `Ø`；
5. 最值得借鉴的一种做法和最不可照搬的一项条件；
6. 所有高负重事实回到原始页面，不继承采集报告的推断。

## 八、停止线

- 同一个 Claude 窗口维持同一个平台；换平台必须由杨明确决定。
- 平台累计 20—30 个后默认停止采集，但不要求把所有对象都拆完。
- 若连续两批都没有产品被杨选中，暂停该平台，检查入口或采集质量。
- 采集数量不计入进展；只有杨实际理解的产品才进入进展计数。
