## 一、90 秒版本

杨当前需要的不是绑定某一个项目的“TutorAI 实习生”，也不是独立作战略判断的产品经理，而是一名能够**替团队学习 AI、评测 AI 应用、制作可复用的 Agent／工作流、结合真实项目给 1 至 2 名同事进行短时教学，并继续协助市场验证**的研究与创新助理。

杨会使用 GitHub、ChatGPT 桌面版和 Codex，也能设计项目和系统指令，但缺少持续学习课程、安装调试、比较工具和反复试错的时间与意愿。岗位首先要承担这部分学习成本：实习生先学、先试、先筛掉无用内容，再把真正能改变团队当前工作的部分用短演示交付给 1 至 2 名同事。

岗位更长期的作用，是帮助团队逐步配置一组能承担稳定任务的“AI 员工”。这些能力可以来自其他公司已经开发的通用 Agent，也可以来自现有 GitHub 仓库、Codex Skill、插件、MCP 或自建应用；实习生负责结合团队任务进行专用化配置、测试、教学和维护。

这名实习生的核心价值依次是：

1. 维护“AI 应用雷达”：发现工具、按团队的真实任务测试，说明什么场景用什么、什么不值得用；
2. 建立“Agent 工坊”：把已经跑通且会重复发生的工作，做成团队能直接调用的 Skill、Agent、插件或其他最小可用形式；
3. 提供“团队短课”：实习生先完成学习和试错，再向 1 至 2 名同事做简单演示和教学，并把有效工具装进真实工作流；
4. 帮助 1 至 2 名同事更好地使用 GitHub、ChatGPT 桌面版、Codex、项目指令、深度研究、RAG 和可组合的开源工具；
5. 替团队执行必须由人完成的市场真人调研、招募、访谈、观察、跟进和验证；
6. 围绕具体产品协调设计、制作、外包、供应商和测试对象，把模糊想法变成下一步可执行任务；
7. 持续发现新产品，为杨提供未经机会总结污染的第一轮筛选材料；
8. 承担 SK 公众号文章的资料核验、排版、发布和发布后基础维护，但这只是基础附带工作，不是岗位成立的主要理由。

岗位可以鼓励创新想法，但首要验收不是“知道多少 AI 名词”，而是能否把一个工具变成 1 至 2 名同事实际用得上的能力，并可靠推进现实任务。实习生可以提出判断，不能替杨作最终项目裁决。

## 三、建议岗位名称与定位

建议内部名称：

> AI 应用落地与研究助理实习生（工具评测 × 工作流落地 × 教学 × 市场验证）

用于 BOSS 的对外名称：

不建议只称为“AI 老师”“产品经理实习生”“AI 工程师”或“市场负责人”。目前真正需要的是一名 AI 应用研究与学习转译型执行助理：能替团队筛选和跑通工具，用普通语言向 1 至 2 名同事讲清楚，把重复工作封装成可用 Agent／工作流，再用于研究、产品和真人验证。

## 四、岗位使命

> 把 AI 工具学习、安装调试、功能筛选、Agent 评测和第一轮试错从主要决策者身上移走，让 1 至 2 名同事用少量时间掌握对当前项目真正有用的能力，或直接获得可以调用的 Agent／工作流；再帮助团队把模糊想法推进成有对象、有动作、有记录、有现实反馈的下一步。

岗位不是单纯资料整理，也不是被动等指令。合格的助理应能在杨给出目标后：

1. 判断这个任务是否值得引入新工具；
2. 自学、安装、试跑并筛掉不适用方案；
3. 用一个真实任务向 1 至 2 名同事做短演示，并留下最小操作说明；
4. 把项目目标拆成可执行清单，找到需要接触的人和资源；
5. 准备沟通材料并取得授权，执行、记录和跟进；
6. 如实报告成功、拒绝、失联、错误和未知；
7. 提出下一步建议，等待杨裁决。

## 五、工作模块与优先级

### P1｜AI 工具学习、工作流落地与团队短教学——岗位的第一承重任务

实习生不需要入职时精通所有工具，但必须能完成“自学—实跑—演示—留档”的闭环：

- 定向学习 GitHub、Codex、ChatGPT Work／桌面版、Claude Code 及项目当时需要的其他工具；
- 用真实但不敏感的小任务跑一遍，而不是只复述课程；
- 向 1 至 2 名同事做 10—30 分钟的简明演示：为什么现在值得学、能做什么、不能做什么、最适合什么任务；
- 留下一页式操作说明、示例、常见失败和升级路径；
- 比较工具带来的实际时间节省、错误、人工复核和账号成本；
- 对团队常做的流程提出自动化或半自动化建议，并先做小样；
- 帮助团队建立可持续的 ChatGPT／Codex 项目结构、上下文管理、任务拆分和验收方式；
- 针对真实任务迭代系统指令，并用失败样例和验收结果判断是否改进；
- 把市场研究、深度研究、资料核验、报告生成和多人／多工具协作组装成可重复流程；
- 对 GitHub 项目先核用途、安装要求、许可证、维护活跃度、数据与凭证风险，再决定是否试跑；
- 对值得采用的开源项目完成安装、最小示例和退出／卸载说明；
- 不把“新功能很多”当成必须采用的理由。

#### 本地部署不以“页面打开了”为完成

一个 GitHub 项目只有同时完成以下事项，才算达到可交付部署：

- 查清操作系统、运行环境、依赖、硬件、账号和费用要求；
- 使用单独测试环境完成安装，不污染杨的主要工作环境；
- 保存准确版本、配置步骤和必要命令，不依赖候选人的个人记忆；
- 用代表性输入测试核心功能，并与项目宣称或基线比较；
- 能读日志、定位常见错误，无法修复时说清阻塞位置；
- 用普通语言解释数据怎样进入、核心模块怎样处理、结果怎样出来；
- 标明数据上传位置、API Key、许可证、网络、隐私和供应链风险；
- 重启后仍能复现，并提供更新、备份、停止和卸载办法。

每项学习任务的完成标准不是“实习生学会了”，而是至少满足以下一项：

1. 杨经过短演示后能独立完成一个真实任务；
2. 实习生把流程代为运行，并能稳定交付杨需要的结果；
3. 实测证明工具不适用，从而停止继续投入。

### P2｜Agent 评测、选择与原型——岗位的第二承重任务

#### “AI 员工”的内部定义

“AI 员工”是便于杨理解的内部称呼，不代表它具有人的法律身份、责任能力或可以无人监督地代表杨行动。这里指的是：

> 一个围绕明确岗位任务配置，拥有规定资料、工具、流程、输出、权限、验收和人工升级边界的可重复 AI 能力。

每名“AI 员工”应有一张岗位卡：

- 名称及唯一任务；
- 谁在什么场景调用；
- 需要什么输入，交付什么输出；
- 允许读取哪些资料、调用哪些工具；
- 可以自行完成什么，哪些动作必须请杨批准；
- 依据哪些来源，如何显示引用；
- 典型成功样例、失败样例和拒绝条件；
- 时间、调用费用和人工复核成本；
- 谁维护，何时复测、停用或替换。

#### “微调”优先理解为专用化配置

杨所说的“把第三方通用 AI 员工微调好”，第一阶段通常不需要训练模型权重。优先按以下顺序专用化：

1. 写清岗位任务、输入、输出和停止条件；
2. 配置系统指令、示例和输出格式；
3. 接入经过治理的仓库资料或 RAG；
4. 配置 Skill、插件、MCP、脚本和其他工具；
5. 设置账号权限、人工审批和隐私边界；
6. 用代表性任务和失败样例评测；
7. 根据真实使用修订，并保留版本和回退办法；
8. 只有上述办法仍无法解决稳定、可测的行为缺口时，才评估真正的模型 fine-tuning。

AI 员工有三条取得路线：

- **买／采用：** 使用别家公司已经开发的 Agent 产品或 Agent，再进行专用化配置；
- **改／封装：** 把现有仓库、脚本、Skill、插件、MCP 或工作流组合成杨可以调用的能力；
- **做：** 当现成能力无法覆盖稳定任务时，再开发新的 Agent 或应用。

默认先采用、再配置、再封装，最后才自建。实习生的价值不是制造更多 Agent，而是帮助杨得到更少但真正能工作的 AI 员工。

“做一个 Agent”不是单一技术动作。实习生拿到一个仓库或重复任务后，应先判断最轻的合适形态：

| 真实需要 | 优先形态 | 不应误做成什么 |
|---|---|---|
| 只执行一次的临时任务 | 当前对话中的清楚任务说明 | 不为一次任务造长期 Agent |
| 某个仓库每次都必须遵守的规则 | `AGENTS.md` | 不把所有规则塞进一个超长系统指令 |
| 重复发生、步骤和验收稳定的工作 | Skill，必要时附脚本、参考和模板 | 不先开发独立应用 |
| 需要读取外部系统或执行外部动作 | MCP 工具或连接器，再由 Skill 定义流程 | 不用复制粘贴冒充实时连接 |
| 需要安装、共享一组 Skill／连接器／MCP 能力 | 插件 | 不把分发问题误当模型问题 |
| 需要持续状态、多工具编排、审批、护栏和运行追踪 | 独立 Agent 程序或 Agents SDK | 不在没有稳定任务前过早工程化 |

上述形态不是互斥关系。官方 Codex 文档将 `AGENTS.md`、Skills、MCP 和 Subagents 定义为互补层：仓库规则负责长期行为，Skill 封装可重复流程，MCP 连接外部工具与上下文；插件则可把 Skill、连接器和 MCP 能力打包分发。真正需要代码级编排、状态、审批、护栏和运行追踪时，再考虑 Agents SDK。参考：[Codex Customization](https://learn.chatgpt.com/docs/customization/overview)、[Save workflows as skills](https://learn.chatgpt.com/use-cases/reusable-codex-skills)、[Plugins](https://learn.chatgpt.com/docs/plugins)、[Agents SDK](https://developers.openai.com/api/docs/guides/agents#compare-the-responses-api-and-agents-sdk)。

因此，“现有仓库做成 Agent”要逐项拆解。一个仓库可能只是：

- Agent 需要读取的知识与规则；
- 可以由 Skill 调用的脚本；
- 可以封装为工具的程序；
- 可以通过 MCP 暴露的外部能力；
- 一个真正独立 Agent 应用的代码基础；
- 或者只是一个看起来有趣、但与杨当前任务无关的项目。

#### Agent／AI 工具评测流程

每个候选工具或 Agent 至少完成：

1. 写清目标使用者、具体场景、输入、输出和不能失败的环节；
2. 设定当前人工方法或直接使用通用 ChatGPT／Codex 的基线；
3. 准备 5—10 个代表性任务，包含正常、模糊、缺资料、反例和危险动作；
4. 分别记录任务完成率、事实错误、人工介入分钟数、运行时间、现金／调用成本、权限与隐私风险；
5. 测试错误触发、拒绝、审批、来源追溯和重复运行是否稳定；
6. 给出四选一结论：直接使用／人工复核后使用／继续原型／停止；
7. 不做跨量纲合成总分，不用漂亮演示抵消事实错误、权限风险或无法复现。

#### 每个可交付 Agent 的最小包

- 一句话说明“什么时候用它”；
- 入口、输入和预期输出；
- 需要的账号、权限、数据和费用；
- 5—10 个测试任务及结果；
- 已知失败、人工复核点和停止条件；
- 安装／调用演示；
- 更新、禁用和卸载办法；
- 谁维护、多久复测一次；
- 一次由 1 至 2 名同事亲手完成关键动作的验收。

VentureLab 仓库级 Skill 仍受既有治理门约束：同一流程至少独立运行两次，并至少一次实际减少漏项／返工或影响候选取舍后，才提议正式建立。实习生可以先做测试原型，不能为了展示产出批量制造 Agent 或 Skill。

### P3｜真人调研与市场验证——Agent 的现实应用线

实习生可在杨明确项目、对象、口径、预算和边界后：

- 寻找符合条件的访谈对象、用户、购买者、使用者或行业人员；
- 通过已有关系、公开社群、线下场景和合规渠道发出招募；
- 安排时间、确认知情和记录方式、管理提醒与取消；
- 按经过批准的提纲访谈，不替受访者总结其没有说过的需求；
- 记录原话、具体行为、当前替代、付款或拒绝边界；
- 对关键回答追问时间、频率、场景和最近一次真实行为；
- 整理去身份化纪要，区分事实、转述、推断和空格；
- 跟进样品、原型、报价或使用后的真实反馈；
- 使用 AI 辅助转写、整理和检索，但由人回听、核验和保护隐私；
- 记录拒绝、无回应、退出、退款和负面评价，不只交成功案例。

**边界：** 未经项目级授权，不得自行承诺价格、效果、合作、报酬或长期关系；不得用熟人礼貌反馈冒充市场需求；涉及未成年人、敏感个人信息和受监管场景时另设更严格边界。

### P4｜仓库智能化与 RAG 协作

RAG 指“让 AI 在回答时检索我们自己的可靠资料，再基于检索结果作答”。实习生可承担：

- 整理文档命名、元数据、标签、版本和来源链接；
- 识别重复、过期、互相冲突和不宜进入检索库的材料；
- 准备小规模标准问答和召回测试集；
- 比较关键词检索、语义检索和混合检索的效果；
- 记录错召回、漏召回、过期材料污染和来源无法追溯的问题；
- 在负责人选定的工具中做小范围原型；
- 把可重复流程写成短说明或演示，而不是建立另一套方法论文档。

“仓库越用越聪明”不能写成 RAG 会自动学习。可持续变好的闭环至少是：

```text
新材料进入
  → 来源、权限、时间与版本检查
  → 去重、结构化与可检索处理
  → 用固定问题测试召回和回答
  → 记录漏召回、错召回、过期引用和真实使用反馈
  → 人工确认哪些修订可以进入知识库、规则或 Skill
  → 版本化更新并重新测试
```

候选人需要理解并能逐步实现：

- 文档切分、元数据、索引、检索和引用追溯；
- 关键词、语义和混合检索的差异；
- 资料新鲜度、冲突、权限和失效关系；
- 一组固定问题及预期来源，用来判断系统是否真的变好；
- 用户反馈如何进入待审队列，而不是直接污染正式知识；
- 何时只需增强当前仓库，何时才值得增加界面并形成独立应用。

**边界：** 仓库结构、证据定义、长期规则和跨仓权限仍由各仓规则与杨裁决；实习生不得因为技术方便批量导入隐私材料、低质量报告或受版权限制内容。

### P5｜产品发现与第一轮筛选

建议将“每天找几个产品”设计成稳定但轻量的产品雷达：

- 从官方榜单、众筹、零售新品、创作者演示、行业媒体和专业社群发现具体产品；
- 每个对象至少保留产品名、具体 SKU／型号、原始页面、演示材料、价格和被用户选择的可观察线索；
- 标明来源利益关系和哪些关键结果尚未核验；
- 去重并排除只有概念、没有具体产品主体的材料；
- 先给杨看原始页面和演示，不预先用“这是机会”污染杨的第一眼；
- 杨选中后，再补评论、失败、当前替代、供给和行动参数。

**建议节奏 `I·待杨确认`：** 每个工作日提供 3 个紧凑对象，每周只深拆杨选中的 1—2 个。数量不是绩效；连续提交低质量、重复或无法核原页的对象不算完成。

### P6｜产品制作、外包与合作协调

在具体项目中，实习生可以：

- 根据杨的想法整理一页式需求简报；
- 寻找设计师、工程师、供应商、打样方、摄影／视频和其他外包资源；
- 准备询问清单，收集报价、周期、交付物、修改次数和权利归属；
- 安排沟通、整理纪要、跟踪待办和验收材料；
- 协助样品收发、测试安排、版本比较和问题复现；
- 建立候选资源对照，不用单一报价替代质量、可靠性和迁移风险判断。

**边界：** 签约、付款、知识产权裁决、最终供应商选择和对外承诺由杨负责；任何现金支出和个人信息提供须事前授权。

### P7｜SK 公众号基础运营——附带任务

在另获 SK 仓库与账号权限后，可承担：

- 按既有底稿完成格式整理、图片和链接检查；
- 核对标题、摘要、引用、错别字和移动端展示；
- 建立待发布清单并按杨终审版本操作发布；
- 保存发布链接、时间和基础反馈；
- 根据杨的批注修改，但不擅自改变文章结论。

这项工作不应成为主要筛选标准。即使操作简单，公开发布仍必须经过杨终审；账号凭证采用最小权限，不通过聊天或公开仓库保存。

### P8｜创新提案——加分项，不是替代执行

欢迎实习生：

- 从调研、产品观察和工具试用中提出新产品或改良想法；
- 说清目标用户、当前替代、具体差异和最便宜的反证办法；
- 主动指出杨方案中的反例、执行困难和已有等价方案；
- 将想法写成一页提案，而不是直接包装成已成立项目。

创新意识可以加分，但不能抵消诚信、可靠性、真人沟通和交付能力的失败。

“赚钱想法”也必须落到具体对象、购买行为、当前替代、我方可控制差异和现实验证动作。能主动提出产品想法、反例和验证办法者优先；只会使用“市场很大、AI 很火、可以收费”等表述不构成加分。

## 六、还可以移交给实习生的工作

以下任务适合逐步移交，但应先给模板或验收例子：

1. 维护项目联系人、跟进时间和下一动作清单；
2. 管理访谈招募、提醒、纪要确认和激励发放记录；
3. 整理竞品账号、试用状态、价格和取消节点；
4. 对公开材料做原始链接恢复和事实核验；
5. 把语音、会议和零散观察整理成结构化待核纪要；
6. 跟踪样品、原型和外包版本，记录谁在何时改了什么；
7. 为产品测试准备脚本、表格、招募文案和说明材料；
8. 组织小型线下体验、公开展会或门店观察，前提是边界和预算已确认；
9. 维护每周“新产品雷达”和杨的已看／跳过／待补证状态；
10. 做工具功能更新侦察，只报告会改变现有工作流的变化；
11. 建立重复工作的短操作说明和检查清单；
12. 汇总一周中的现实信号、未回应、阻塞和需要杨裁决的事项；
13. 协助招聘或管理短期外包人员，但不独立承诺合作条件；
14. 做产品页面、问卷、招募文案和演示材料的基础可用性检查；
15. 在明确授权后执行客户回访、样品使用跟进和流失原因记录。

## 七、不能默认移交的责任

- 选择公司长期方向或判定项目已经成立；
- 代表杨承诺价格、合作、投资、录用、合同或交付结果；
- 未经终审发布代表杨、SK 或 VentureLab 的结论；
- 自行接触未成年人或处理敏感、健康、财务等高责任数据；
- 保存杨的主账号密码、支付凭证或不必要的仓库权限；
- 为了得到“好结果”诱导受访者、隐藏拒绝或修改原话；
- 把 AI 生成内容、公司宣传或单个熟人意见当作真实市场验证；
- 未经授权支出、下单、签约或把工作再外包给第三方；
- 以毕业设计公开项目未披露信息、个人信息或我方尚未公开资产。

## 八、理想候选人画像

> 一名在读大四学生或研究生，优先在长沙，英文技术阅读能力达到岗位要求；对 AI 应用、Agent 和开源项目保持主动学习，能亲自安装、试跑、设计测试、排错并用普通语言向 1 至 2 名同事讲清楚；能把稳定流程做成轻量可复用工具，同时沟通自然、执行可靠，愿意联系真人并接受拒绝。

### 8.1 不可抵消的硬门

1. **身份阶段：** 大四或在读研究生；
2. **英文技术阅读：** 能读取官方文档、README、Issues、错误日志和许可证，并准确用中文复述；CET-6 已通过只作为申请阶段的初步证明，未通过者可通过统一现场测试证明符合；无论是否通过六级，证书均不能替代实际能力核验；
3. **诚信：** 不伪造来源、访谈、作品和个人贡献；
4. **可靠性：** 时间承诺现实，按时交付，问题提前报告；
5. **英文信息校准：** 能区分原文明确陈述、工具翻译、自己的解释和仍不确定之处；涉及版本、限制、权限和风险时愿意回到原文核对；
6. **表达与教学：** 能把复杂工具按“为什么用—怎样用—哪里会失败”讲给非技术使用者；
7. **AI 自学与迁移：** 已能使用 Codex、ChatGPT Work、Claude Code 等至少两类工具，并能在限定时间内学会第三类陌生工具；
8. **本地部署与排错：** 能使用 Git、终端、环境变量和至少一种常用编程语言，处理安装、依赖、配置、日志和常见报错；
9. **AI 核验意识：** 知道 AI 和开源项目都会出错，愿意查看原始文档、真实测试并报告失败；
10. **评测意识：** 能建立基线和测试样例，不凭一次漂亮演示断言工具有效；
11. **真人沟通：** 愿意招募、追问、跟进，也能尊重拒绝；
12. **保密与权限：** 接受最小权限、隐私和公开发布边界；
13. **助理心态：** 愿意处理具体、重复、琐碎但承重的执行工作。

### 8.2 优先但非必须

- 入职时已有 RAG、MCP、Skill、插件或 Agent 实作经验；没有相关经历者，需在入职后四周内证明能够学会并完成一个小型可测试结果；
- 当前在长沙高校学习或能稳定线下协作；
- 毕业设计能与 AI 工具、用户研究、产品创新、知识库、RAG、市场验证或当前具体项目结合；
- 有访谈、社团招募、活动组织、销售、客服、田野研究或用户研究经历；
- 有产品设计、工业设计、交互、内容制作、供应链或项目协调经验；
- 有 AI 工具实测、自动化、知识库或轻量编程经验；
- 有安装、修改或实际使用 GitHub 开源项目的记录，能说明失败和排错过程；
- 使用过 Python 或 TypeScript／JavaScript、Docker、API、数据库、向量检索或常见 Agent 框架中的若干项；
- 做过 RAG 评测、提示词／系统指令评测、MCP、Skill、插件或 Agent 运行追踪；
- 能说明一个系统为什么选择某种模型、检索、工具和人工复核边界；
- 有公众号、校园媒体、研究简报或其他公开内容运营经验；
- 有持续发现、拆解或制作新产品的个人作品；
- 能展示一次从不熟悉到跑通、再教会别人的学习经历。

### 8.3 不作为能力替代的信号

- 学校名气；
- 专业名称；
- 六级分数高但无法准确阅读和复述；
- “会用 ChatGPT”但没有实跑记录；
- 能按 README 安装，但解释不清数据流、核心依赖、风险和失败边界；
- 做过 RAG 演示，但没有固定测试问题、来源引用和错召回记录；
- 做过很多 Agent，却没有真实复用、评测、维护和停用记录；
- 比赛奖项但说不清本人贡献；
- 想法很多但不愿联系真人和做跟进；
- 简历写“产品经理”但没有把任何任务推进到现实反馈；
- 毕业设计题目相关但数据、知识产权和时间安排不现实。

## 九、毕业设计的结合方式

毕业设计相关是双向加分：候选人可能投入更深，我方也能获得持续研究和原型产出。但必须在录用前明确：

- 学校是否允许使用实习项目；
- 导师、学生和项目三方对题目与交付的预期；
- 哪些资料可以公开，哪些必须匿名或不得进入论文；
- 代码、数据、设计、文档和产品成果的权利归属；
- 论文答辩时间是否会挤压实习承诺；
- 若项目停止或换方向，毕业设计能否保留独立完成路径；
- 不得为了满足论文完整性制造访谈、夸大效果或阻止项目及时停止。

毕业设计相关应为优先项，不宜要求所有候选人必须用我方项目毕业，否则会造成项目方向与学生毕业风险相互绑架。

## 十、建议的工作分配

由于项目尚未固定，建议采用“稳定底盘＋阶段主任务”：

- **40%：AI 应用自学、实跑、短教学和场景地图；**
- **25%：Agent／Skill／工作流评测与原型；**
- **15%：当前唯一主项目的真人调研、验证和执行协调；**
- **10%：新产品雷达与入选对象补证；**
- **5%：SK 公众号基础运营；**
- **5%：自由创新提案和流程改进。**

该比例只是起点建议，不是永久制度。每周只指定一个第一优先项目；新任务进入时，必须明确替换或后移什么，避免“什么都做”变成所有工作都没有闭环。

### 10.1 薪资与投入时间口径

杨已确认以日薪作为主要招聘和结算口径，对外统一发布为 **150—200 元／天**：

- 大四学生通常从 **150 元／天**起，根据已验证能力可提高，原则上不超过 **200 元／天**；
- 研究生可参考 **200 元／天左右**，但学历本身不自动决定报价；
- 候选人能否独立学习、部署、测试、教学并形成被真实使用的交付，是确定具体日薪和后续调整的主要依据；
- 表现调整应在约定的复盘节点明确，不使用模糊的“以后有机会加薪”替代当前报酬约定。

复盘节点统一为：满四周复盘岗位适配、实际交付和具体日薪；满十二周复盘是否续期、是否扩大职责，以及是否再次调整待遇。

原先提出的每月 **4,000—6,000 元**不再作为所有候选人的固定月薪口径。它只可能出现在较高出勤、较高能力或表现调整后的具体组合中；月度预估必须按“约定日薪 × 实际出勤天数”计算。例如，150 元／天按每月 22 天计算约为 3,300 元，不能再同时宣传为 4,000 元固定月薪。

时间口径确定为：每周至少投入四天，能够稳定投入五天者优先；每天按八小时计为一个工作日，不含通勤和午休；原则上至少连续实习三个月。入职后的前两至四周是双方磨合期，按同一日薪结算并计入实习周期。

招聘信息还应同时写清：

- 日薪；
- 每周至少投入几天；
- 每天按多少小时计为一个工作日；
- 是否接受半天或远程投入；
- 月度金额只是按约定出勤估算，最终按实际出勤或双方约定结算；
- 真人调研交通、受访者激励、AI订阅、样品和其他项目支出另行报销，不包含在实习工资内。

候选人主动询问薪资、工时和结算方式属于正常行为，不作为负面信号。真正需要识别的是：候选人是否只愿意完成最低限度工时，却不愿学习、试错、承担真实任务或提高能力。岗位的学习机会是重要吸引力，但不能替代清楚、按约履行的劳动报酬。

### 10.2 已确定的首个四周任务｜创新智能 AI 仓库关联召回 L0 验证

首月不漫无边界追踪 AI 新闻，也不先开发庞大的 RAG、多 Agent、知识图谱或界面。围绕 VentureLab 的一个真实问题完成闭环：当一个新观察、灵感或产品进入时，能否从批准范围内的既有材料中找回最相关的 3—5 条旧构思、产品、失败记录或历史裁决，并说明为什么相关、能证明什么和不能证明什么。

1. **第一周｜边界与手工基线：** 熟悉批准目录、隐私和只读边界；用一个正在影响当前取舍的真实输入，手工完成首次关联召回，留下来源路径、关联理由、误召回和漏召回；
2. **第二周｜三个真实回合：** 再完成至少两个独立真实输入，对照杨原本准备怎样判断，以及召回后是否改变下一问题、验证动作、合并或停止决定；不为凑数虚构测试题，不用新增文件数量冒充价值；
3. **第三周｜有条件的轻量实现：** 只有前三个真实回合中至少一次出现可追溯的判断或行动变化，才建立最简单的检索基线；优先使用现有索引、关键词和必要元数据，确认简单方案不足后才讨论语义检索。没有增量时允许停止专门实现；
4. **第四周｜盲测、试用与交付：** 使用预先保留的 10 个真实输入，比较人工基线与工具结果，分别记录前 5 条召回质量、来源追溯、决策增量、人工时间、误召回和漏召回；再向 1 至 2 名同事做一次 20—30 分钟短演示，由至少一名同事亲手提交一个真实输入或核对一组结果，最后形成继续、修改或停止建议。

四周验收不使用综合分数，也不把文档、界面和 Agent 数量当作成果。建议观察线为：10 个输入中至少 7 个的前 5 条结果包含已知相关材料；每条结果有准确路径和关联理由；至少两次找回原本会遗漏的信息并改变下一问题、验证动作、合并或停止决定。未达到时可以回到普通人工检索，不为保住项目继续堆功能。

短演示用于检验结果能否被别人理解和调用，不能替代召回质量与决策增量。参与试用的同事、共同操作时间和可用账号由杨提前协调；因同事未按约参与导致无法完成试用时，单独记录，不直接算作实习生失败。

本任务默认只读，不自动开放 `private/`、候选人材料、家庭材料、未脱敏访谈、账号或密钥；不授权批量重构仓库，也不授权联系真人、询价、购买、拿样、发布、报价或售卖。需要写入时使用单独分支和最小文件范围，由杨或指定复核者验收后合并。

### 10.3 候选人的真实成长收益

这份岗位不能只对杨有利。对合适候选人，希望三个月后至少留下以下四类成果：

1. **一个完整案例：** 能从头讲清问题怎样出现、怎样形成构思、做过哪些动作、现实怎样反馈，以及为什么继续、修改或停止；失败和停止也可以是有效结论；
2. **一份可展示作品：** 可以是 AI 工作流、工具、产品原型、评测或验证记录；涉及公司、用户和第三方的信息先脱敏，并在保密和知识产权允许的范围内进入作品集、毕业设计或后续面试；
3. **共同构思与实践记录：** 如果候选人提出了被实际采用的产品路线，并亲自推动用户反馈、原型、样品或其他现实验证，仓库应按原始观察、方案提出、验证主导和最终取舍分别记录其具体贡献，不用“团队完成”抹平；
4. **一条个人创新支线：** 候选人可以从自己真实遇到的问题出发，提出一个由本人主导的构思，在不占用主项目交付、不过度使用公司保密材料的前提下，练习用户、当前替代、不同解法、最小原型、反例和停止条件。

岗位希望通过反复的小回合培养创新习惯，而不是只讲创新概念：观察一个真实动作，找出现有替代，区分口头抱怨与行为，提出 2—3 条原理不同的改法，选择最便宜的验证，事先写停止条件，接触现实，再记录自己哪里判断错了。每周复盘采用“行动前预测、行动后对答案”，让判断力由结果校准。

公司任务、共同孵化和个人创新必须分开记录。共同构思者或实践者身份只表示具体贡献得到承认，不自动等于联合创始人、股东、合伙人、专利权人或商业收益权人；个人创新也不得默认带走公司的保密资料、专属方案和未公开证据。若某个共同或个人构思准备进入专利、生产、销售、融资或其他商业化行动，应在行动前另行书面确定成果归属、署名、使用权和合作方式。

这些学习和认知收益是岗位的重要吸引力，但不替代工资，也不构成职业、创业、投资或产品成功保证。对外可以表达“有机会成为产品的共同构思者和实践者，并形成个人创新支线”，但只能在确有相应任务、贡献记录和现实验证条件时兑现，不能把可能性包装成入职即得的承诺。

## 十一、建议筛选流程

具体问题、现场实操套题、面试官观察表和记录模板统一见 [`招聘面试与实操题库-AI应用与Agent实习生.md`](招聘面试与实操题库-AI应用与Agent实习生.md)。题库只供内部抽题使用，不整体发送给候选人。

### 门 1｜申请材料与硬门确认

申请人提供：

- 一页简历；
- 学校、年级、专业、预计毕业时间和是否在长沙；
- CET-6 状态；已通过者可附记录，未通过者不因此自动退出，但需在面试中通过统一英文技术资料阅读测试；
- 每周可投入时间及毕业设计、考研、求职安排；
- 一个最能代表 AI 应用评测、Agent／自动化、工具落地、执行、调研或产品能力的既有作品；
- 200 字说明：学会一个新工具后，如何在 15 分钟内教给一个没有基础的人；
- 200 字说明：曾经联系陌生人、组织活动、完成访谈或处理拒绝的一次经历；
- 如希望结合毕业设计，说明初步题目、导师状态和公开边界。

无偿申请总耗时不超过 30 分钟，不要求为项目制作新方案。

### 门 2｜结构化面试

重点核验：

- 项目和作品中本人真正负责的部分；
- 英文资料阅读实测：标准面试先使用国际 AI 产品的官方定价页、功能页、帮助页或 Release Note 做 7 分钟短测。候选人可使用日常工具，但必须说明产品用途、适用对象、条件、限制、原文事实、个人推断和仍不确定之处，并当场定位、解释随机指定的关键原句。短测不能形成稳定判断时，另行使用 15 分钟 README、Issue／报错和权限或许可证材料做强化核验，不在同一场面试叠加；
- 面对一个没用过的 GitHub 项目，会如何判断是否值得装、如何安全跑通、如何教给别人；
- 能否把系统指令、工具和流程的改进落到可重复测试，而不是凭感觉声称“最优”；
- 能否把模糊目标拆成联系人、动作、时间和验收；
- 面对陌生人拒绝、失联和含糊回答时如何处理；
- 能否区分用户原话、自己的解释和市场事实；
- 如何学习陌生 AI 工具并判断它是否真的有用；
- 是否接受琐碎执行、版本记录、保密和最小权限；
- 毕业、论文、考研或求职是否影响稳定投入。

### 2026-09-21 英文要求裁决

英文技术阅读能力继续作为不可抵消的硬门；CET-6 从资格硬门调整为申请阶段的初步证明。未通过 CET-6 的候选人可通过统一现场英文技术资料阅读测试证明符合；无论是否通过六级，证书均不能替代实际能力核验。此前仅因未通过 CET-6 而退出、其他条件仍可能符合的候选人，可按同一标准重新进入一次定向核验，不对个别人临时降低标准。

### 门 3｜面试内限时实操

不设置独立的两至三小时有偿工作样本，也不把它改成无偿真实业务任务。在结构化面试中安排 **30—45 分钟现场实操**：

1. 使用公开或模拟材料，不接触未公开项目、真实账号和外部对象；
2. 给候选人一段陌生工具说明、GitHub README 或报错信息，以及一个明确的小任务；
3. 观察候选人如何澄清目标、查找信息、判断风险、说明卡点并组织表达；
4. 不要求完整部署，不要求留下可直接用于我方业务的成果；
5. 能诚实说明“不知道”“当前跑不通”或“这个工具不值得用”，并给出依据，同样可以合格。

### 门 4｜有偿短期协作

先用 2—4 周边界明确的真实任务观察：

- 能否把工具真正跑通并教会 1 至 2 名同事；
- 能否判断某个 GitHub 项目值得继续、停止或换用更简单方案；
- 能否在没有作者现场帮助时，依据英文文档和日志复现安装与核心测试；
- 能否解释数据流、核心模块和错误可能发生的位置；
- 能否判断一个需求应停留在任务说明、做成 Skill、连接 MCP、打包插件还是开发 Agent；
- 能否持续找到并跟进真人；
- 能否从零散工作中维护清楚的下一步；
- 是否如实报告失败和错误；
- 是否需要杨投入过多管理时间；
- 是否能在项目切换时保留记录并完成交接。

## 十二、首期验收标准

首期不使用跨量纲总分，分别观察：

- 从接到新 AI 工具到可演示需要多少时间；
- 杨是否在演示后能独立完成一个真实任务；
- 有多少工具真正进入工作流、多少被有理由停止；
- 安装和试用开源项目时，是否识别许可证、数据、凭证、依赖和维护风险；
- 制作的 Agent／Skill 是否在代表性任务和失败样例上可重复运行；
- 完成了多少次合格真人接触、访谈、跟进或测试；
- 原始记录是否完整，是否出现诱导、编造或关键遗漏；
- 新产品提交中有多少被杨选择继续看，以及被跳过的原因；
- 外包与合作资源是否取得可比较的真实回复；
- 公众号是否按终审版本准确发布；
- 每周需要杨投入多少管理和返工时间；
- 候选人是否提出过改变产品取舍或验证动作的有效反例与建议。

## 十三、主要风险与处理

### 风险 1｜岗位过宽，招到“什么都懂一点、什么都无法闭环”的人

处理：把 AI 应用学习、Agent 评测、短教学和工作流落地设为第一主能力，把真人调研作为现实应用线；每周只保留一个主项目和一个明确的 AI 学习／Agent 主题。

### 风险 2｜“工具人”被理解为只听指令、不思考

处理：公开岗位不用“工具人”表述。内部期待是高执行力助理：必须能指出问题、提出替代，但最终裁决归杨。

### 风险 3｜创新倾向与助理工作冲突

处理：明确创新是加分项，重复跟进、记录、排版和协调仍是岗位组成部分；不愿做基础执行者不适合。

### 风险 4｜毕业设计绑架项目

处理：毕业设计只做优先项；预先约定停止、换题、公开和知识产权边界。

### 风险 5｜实习生替杨做完“看产品”，反而削弱杨的产品判断

处理：产品雷达先交原始页面和演示，杨先观察；实习生只做初筛、去重和后续补证，不替杨给最终机会结论。

### 风险 6｜真人调研变成礼貌反馈或销售表演

处理：记录拒绝、无回应和替代解释；项目级预登记对象、问题、停止条件和禁止诱导项。

### 风险 7｜招到“AI资讯播报员”，团队仍然不会用

处理：不以课程笔记、工具清单和新闻数量验收。每次必须用团队的真实任务演示；演示后由 1 至 2 名同事亲手完成一次，或明确决定以后由实习生代运行。

### 风险 8｜追逐 GitHub 项目，安装和维护成本高于实际价值

处理：先做用途、文档、许可证、维护状态、依赖、数据和凭证检查；只跑最小示例。不能在短周期内说明对当前任务的具体价值时停止，不为“项目看起来厉害”持续投入。

### 风险 9｜把每个仓库和流程都包装成 Agent

处理：先走最小形态判断。一次性任务留在对话，长期规则放 `AGENTS.md`，稳定重复流程才考虑 Skill，需要外部系统再接 MCP；只有轻量方案不能满足持续状态、工具编排、审批和追踪要求时，才开发独立 Agent。

### 风险 10｜Agent 数量增加，但没有真实任务复用

处理：Agent 数量不计作岗位成果。只有被团队实际调用、在重复任务中减少人工或错误，并留下测试和停用办法，才算有效交付。

- 默认测法改为面试官能够核对的 7 分钟国际 AI 产品官方资料短测，以原文定位、限制识别和即时解释为核心；
- 15 分钟两阶段技术材料测试调整为短测结果不明确时的强化核验，不再假设线上面试能够可靠监管候选人的另一块屏幕，也不在同一场面试连续叠加。

## v1.1 变更记录

- 英文技术阅读能力继续作为不可抵消的硬门；CET-6 从资格硬门调整为申请阶段初步证明；
- 统一现场测试为两段式：前 5 分钟不使用生成式 AI、后 10 分钟允许使用 AI；所有进入面试的候选人均需接受实际能力核验；
- 此前仅因未通过 CET-6 而退出、其他条件仍可能符合的候选人，可按同一标准重新进入一次定向核验。
